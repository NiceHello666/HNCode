feat: every diagnostic log now rotates at 5 MB, keeping one generation

NO CEILING, NO CLEANUP.

`paint.log` reached 174 MB on this machine and `keys.log` 7 MB, and nothing ever
rotated or removed either: each was a bare `fs.appendFileSync`. `session-errors.log`
grows by a line per failed save, so an unattended session stuck on one failure grows
it without limit — and buries the very error it exists to record. On a machine with a
small disk that is the difference between working and not.

All four now go through `src/log-file.js`.

  * The ceiling is measured on the file's own length, checked BEFORE the append, so
    the live file never grows past it. Rotating after the write left no live file at
    all until the next write created one.
  * One generation is kept, `<name>.1`. A debug log is read right after the event that
    wrote it, so a second generation would only preserve the moment before the one
    being investigated, at twice the disk.
  * A record larger than the whole ceiling becomes the rotated file and the live log
    is left present but empty. Truncating it instead would cut the stack trace that
    made it worth recording.
  * The append is a single `appendFileSync`, which is O_APPEND and atomic per record,
    so two hncode instances sharing a log interleave rather than clobber. Only the
    rotation can race, and the loser's rename fails harmlessly.
  * It never throws: a log is not worth the failure it would add to the path doing the
    logging.

The size is cached between writes, so a burst costs one `statSync` (measured 33 us)
rather than one per record. `paint.log` writes sit behind HNCODE_TRACE_PAINT and
`keys.log` behind HNCODE_TRACE_KEYS, so that cost is only paid while tracing.

test/log-file.test.mjs covers the ceiling, the single generation, the oversized record,
that the live file always exists, and that an unwritable target returns false.
