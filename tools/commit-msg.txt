fix: a session could corrupt itself on save, and was then overwritten empty

A CONVERSATION DESTROYED BY ITS OWN WORDS.

`stringifySession` spliced the message array into a placeholder with
`text.replace(pattern, messagesJson)`. A replacement STRING is not literal text:
`$&`, `` $` ``, `$'` and `$$` are expansions. A message that merely mentioned
`sed s/x/$&/g` therefore spliced a copy of the session's own metadata head into its
own JSON, and the write is tmp-then-rename with no verification, so the damaged
bytes replaced the good ones.

The consequence was not "the session looks odd", it was total loss in three steps:
the file stopped parsing; `loadSession` returned null; `latestSession` fell back to
`pick.meta`, which is metadata only — no messages; the TUI then saved, writing
`messages: []` over the history. Three real sessions on this machine are in that
state, one with 706 rounds and 1519 recorded calls and no conversation left.

Two fixes, because one is not enough.

THE WRITE. The replacement is now a function, which is the only form `String.replace`
does not expand. Byte-identical output, and a message may contain any `$` form.

THE READ. A file that fails to parse is recovered rather than written off
(`src/session-recover.js`):
  * the metadata block is parsed on its own — it is the SEARCH side of the broken
    replace, never the replacement, so it is intact even when the array is shredded;
  * the placeholder `$&` inserted is removed;
  * on an exact single-save file, the injected head copies are cut out and the file
    reparses whole;
  * otherwise every message OBJECT that still parses is salvaged, and the display
    transcript after it is recovered too.

A salvage can keep half of a tool exchange, so `sanitizeToolPairs` then drops a call
with no result and a result with no call — the protocol rejects both, and a 400 on
resume would be a second failure on top of the first.

THE MARKER. `latestSession`'s metadata fallback now comes back as
`{ ...meta, messages: [], _unrecoverable: true }`, and both the TUI and `-p` refuse
that resume: they say the file is damaged and start a fresh session, leaving the
original untouched. Before, the fallback looked exactly like a session. `_`-prefixed
keys are never persisted, so the marker cannot make a healthy session look damaged.

Recovery keeps the damaged original as `<file>.bak` before rewriting, and logs one
line to session-errors.log saying which route worked and how many messages were
saved.

Verified on the two real damaged files: 485 and 7 messages back, both parse after the
repair, both keep their .bak, both pair every tool call with its result.
